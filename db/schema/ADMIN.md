# Phase 4 internal controls

Migration 0007 enables reviewed Phase 9 deposit-intake OPEN; other unresolved
lifecycle operations remain blocked.
This is a local development CLI, not a production admin interface. No admin HTTP
route, cookie, bearer token, user account or invented authentication system exists.
The admin CLI has no participant-facing HTTP route.

## Authorization and provisioning

Apply migrations as the separate schema owner. Have that owner provision a
dedicated restricted PostgreSQL login with protected libpq authentication. The
login must not have superuser, owner, CREATE DATABASE/ROLE, replication, BYPASSRLS,
private-schema usage, private-table privileges or membership in an owner role.
Do not use the development maintenance credential for runtime admin traffic.
No credentials or login roles are generated by this implementation.

With the owner's protected connection configured, grant only the control entrypoint:

```powershell
node db/admin-provision.mjs <existing-restricted-role>
# Existing Windows owner helper (maintenance only):
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/dev/product-db.ps1 provision-admin -OperatorRole <existing-restricted-role>
```

The grant is USAGE on `darkpool_admin` plus EXECUTE on
`darkpool_admin.command(text,jsonb)` only. Helpers are not granted. The command is
SECURITY DEFINER with fixed `pg_catalog` search path and qualified relations;
it accepts no SQL, policy registration, status assignment or wallet operation.
Provisioning refuses an already overprivileged role; it never silently revokes
existing rights. The CLI independently checks the authenticated login's effective
privileges and rejects owner credentials, including SET ROLE over an owner login.
The trusted database owner can bypass this boundary; this is not owner-proof storage.

For runtime, activate tools and explicitly configure `APP_ENV=development`,
`DARKPOOL_ADMIN_INTERNAL=1`, `ZCASH_NETWORK=testnet`, `PGHOST=127.0.0.1`, `PGPORT`,
`PGDATABASE` and `PGUSER` for that restricted login. Authentication uses protected
libpq configuration/environment, never credentials in command arguments/URLs.
PGOPTIONS/PGSERVICE/PGSERVICEFILE overrides are rejected. Wallet/spending/viewing
configuration is not used. No environment file is loaded automatically.

## Commands

Send one JSON object on stdin to `npm.cmd run --silent admin:dev` (or directly
`node apps/web/src/admin-cli.mjs`). No request or private-record logging is added.
Exit 0 means successful inspect/validation/draft/OPEN processing. BLOCKED and REJECTED exit
1, with an explicit structured result. Error messages never include raw SQL,
PostgreSQL DETAIL, request contents or libpq credentials.

```json
{ "operation": "inspect", "request": {} }
```

| Operation                                     | Request                                                               | Effect                                                                                |
| --------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `create`                                      | `request_key`, `expected_revision: null`, `configuration`             | Create the sole DRAFT market; revision `"1"`; narrow audit event                      |
| `edit`                                        | `request_key`, `expected_revision: "<current>"`, full `configuration` | Replace configuration while DRAFT; increment revision; narrow audit event             |
| `validate`                                    | `configuration`                                                       | Validate draft structure and persisted OPEN readiness; human semantic review required |
| `inspect`                                     | `{}`                                                                  | Explicit configuration/status/revision projection and unavailable-operation reasons   |
| `open`                                        | `request_key`, `expected_revision: "<current>"`                       | Ordinary audited DRAFT -> OPEN when all intake prerequisites pass                     |
| `pause`, `reopen`, `finalize-lock`, `resolve` | `{}`                                                                  | BLOCKED; no mutation                                                                  |

There are no per-ticket reads, operational prediction counts, private book
statistics, audit dumps, receiver mappings, claim/settlement endpoints or signing
functions. `resolve` includes YES/NO/VOID availability only; no outcome/evidence is
accepted or persisted yet. No arbitrary `lock`, `lock-now`, `force` or `set-status`
control exists. Arbitrary PINNED labels do not satisfy the exact approved OPEN allowlist.

Legacy draft configuration has exactly these 19 fields (no defaults):

```text
id, network=testnet, vault_context_ref,
question, yes_definition, no_definition,
opens_at, closes_at,
close_policy_ref, payment_policy_ref, fee_policy_ref,
resolution_rule, resolution_sources[], void_conditions[],
min_stake_zat, max_stake_zat, zero_winner_policy=NO_WINNER_REFUND,
deposit_confirmations, payout_confirmations
```

Policy references must already exist; this interface cannot create/review profiles.
UNPINNED references and nullable thresholds remain representable DRAFT storage;
normal OPEN requires the explicit Phase 9 profile described below.
Threshold numbers, including zero, never constitute policy approval. Amounts are
exact nonnegative decimal integer **strings**, with min <= max; no floating-point
money or economic cap is introduced. Timestamps use exact UTC ISO strings with
milliseconds (`YYYY-MM-DDTHH:mm:ss.sssZ`) and open < close. This transport format
does not choose chain-close mapping/equality or production identifier conventions.
Every draft requires distinct nonempty YES/NO definitions, nonempty proposition/
rule, nonempty source/void arrays and valid referenced policies. Structural
validation cannot prove proposition consistency or source truth/hierarchy.

Administrative request keys contain 1–128 ASCII letters/digits/underscore/hyphen.
They are retry identifiers, not ticket IDs or credentials. Reusing a key with the
same operation and exact parsed JSON request returns the saved original response,
including its historical revision. This contract also covers OPEN. Reusing a key
with different inputs conflicts.
Object key ordering is ignored by JSONB comparison; array order is preserved.
Concurrent edits with the same current revision permit only one new write. All
control operations serialize using a transaction advisory lock; writes, revision,
retry record and audit commit/roll back together. No draft-to-draft lifecycle
transition is manufactured for a configuration edit; audit prior/new states are
both null. Audit source is the authenticated database session login.

Responses omit the private vault reference and policy issue/profile payloads.
They include explicit market definitions, status, revision, configured stake bounds
as strings, nullable confirmation storage and close/payment/fee profile status.
No values are derived from private tickets, payments, wallet activity or claims.
No HTML is rendered by these controls.

The inherited product schema can hold multiple owner-inserted markets for schema
regression fixtures. Runtime admins cannot write those tables: control creation
enforces exactly one market and every control operation fails closed if existing
owner-provisioned state contains more than one. It never silently selects one.
Markets not created through the control boundary can be inspected, but editing
requires its revision record; owner adoption/migration is deliberately unavailable.

## Phase 9 ordinary OPEN

The full intake configuration has exactly 22 fields: the 19 above plus explicit
receiving_policy_ref, close_proof_policy_ref and payout_policy_ref. The three are
required together; no policy labels or confirmation thresholds are defaulted.
Legacy drafts without them remain structurally valid but cannot OPEN.

| Field                                 | Required OPEN value           |
| ------------------------------------- | ----------------------------- |
| close_policy_ref / payment_policy_ref | phase9-exact-chainclock-3-v1  |
| fee_policy_ref                        | phase9-zero-platform-fee-v1   |
| receiving_policy_ref                  | phase9-orchard-receiving-v1   |
| close_proof_policy_ref                | phase9-bounded-close-proof-v2 |
| payout_policy_ref                     | phase9-payout-deferred-v1     |
| deposit_confirmations                 | 3                             |
| payout_confirmations                  | explicit null                 |

Labels use existing policy_refs and market_policy_refs; no new tables or runtime
grants are added. OPEN checks the exact approved profile identities/review
references, one DRAFT market, valid identity/binary event configuration, finite
UTC instants and future immutable close, exact three policy slots, matching
pre-OPEN watcher account/official-endpoint/anchor/deadline binding and no hold.
Existing trusted provisioning supplies the binding while DRAFT; the admin never
opens a wallet or performs chain work. Human semantic review of the proposition,
source hierarchy and void conditions remains necessary. A normal one-hour window
uses these existing timestamps.

OPEN means the market is authorized to accept qualifying Phase 9 deposits. It does not imply settlement, claim, refund or payout readiness.

Platform fee, operator fee and rake are zero. No fee recipient, percentage or
accepted-stake adjustment exists. Wallet/Zcash network transaction fees are
external costs: outside requested/accepted stake, not market rake and not a
participant credit. Payout deferral is explicitly DEFERRED_NOT_REQUIRED_FOR_OPEN,
with numeric threshold null and payout_ready=false; it does not claim reviewed
payout policy. Later payout confirmation/signing policy must be separately
frozen and validated before any payout, claim/refund broadcast or settlement
authorization. REOPEN and other unsupported lifecycle operations remain blocked;
the Phase 9 PAUSED no-new-acceptance behavior is unchanged.

Send operation=open with request containing request_key and expected_revision
(current revision as a decimal string). Parameterless OPEN retains its legacy
non-mutating BLOCKED response; malformed/additional mutation parameters reject.
The normal transition atomically changes DRAFT to OPEN, advances revision, records
MARKET_OPENED with prior/new states, authenticated actor, trigger and profile
evidence reference, and saves the exact replay result. The close is checked again
at UPDATE. Same-key identical retries return the saved response; changed retries,
stale revisions, a different-key OPEN from non-DRAFT, missing prerequisites and
unknown/unreviewed policies reject without mutation. OPEN_PRECONDITION_FAILED is
the fixed CLI error for readiness failure. validate reports READY only when its
configuration matches the persisted ready DRAFT; validation is not a reservation.

Inspect projects the three explicit policy references, deferral state and false
payout readiness in addition to the existing allowlist. It exposes no private
wallet binding, proof, book, receiver or policy-review payload.

Future fresh payment evidence requires separate authorization and a separate new
evidence database containing exactly one market. The successful old evidence
database is preserved. CLOSED still occupies the sole row slot; no archive,
delete, replacement or multi-market operation is introduced. Normal authenticated
CLI tests use only disposable databases and deterministic SQL-only pre-OPEN
bindings, with no wallet, ticket issuance, chain connection or payment.

## Limits and checks

Requests are bounded to 64 KiB at CLI and database entrypoint. Per-field 8 KiB,
array length 1–32, amount-string length 1024 and key length 128 limits bound resource
use; they are not stake/economic policy. No request-size error prints its body.
Ordinary runtime roles receive no table DML, DDL, TRUNCATE or trigger disabling.
The owner must configure server logging, restricted/encrypted backups and runtime
OS isolation; client redaction alone does not disable PostgreSQL statement logs.
Never insert bearer/wallet secrets into configuration text or retry keys.

Run actual synthetic PostgreSQL tests using the maintenance helper:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/dev/product-db.ps1 test-admin
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/dev/product-db.ps1 test
```

Tests create only randomly named `darkpool_phase4_<hex>` databases and matching
temporary restricted login roles, then clean up those exact resources. They never
read wallet SQLite or demonstrate a funded lifecycle. Deferred close, matcher,
pause, ledger, oracle, claim, settlement, refund and payout conformance cases remain
deferred; fail-closed tests are evidence only for these Phase 4 guards.

## PostgreSQL target isolation

Use the explicit protected LIVE_EVIDENCE profile on port 55434 for separately authorized operations; tests use TEST on 55433. HISTORICAL is retired and must not be connected. See the [environment guide](ENVIRONMENTS.md). Existing runtime privilege checks remain mandatory.
